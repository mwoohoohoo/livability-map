# Project Instructions

## Project scope

This repository contains the frontend for the European climbing
suitability mapping project.

It is a Vite/React/D3 application.

The geospatial processing pipeline is maintained separately from this
repository. The external working directory contains the raw datasets,
Python notebooks/scripts and intermediate processing files.

Do not attempt to reconstruct, modify or regenerate the external data
processing pipeline from assumptions made from the frontend code.

## Data architecture

The frontend loads the final web-ready GeoJSON outputs directly from:

- public/data/grid.geojson
- public/data/underlying-grid.geojson

These files are generated outputs from the separate geospatial processing
pipeline and are intentionally tracked in Git because the deployed
frontend loads them directly.

Do not manually edit, reformat, normalize, regenerate or replace these
GeoJSON files from frontend code.

If the contents of these files need to change, identify the appropriate
upstream processing step in the separate data pipeline rather than
modifying the generated files here.

Null component-score values are a known dependency of the upstream data
pipeline.

Do not change Number(null) behaviour or infer the semantic meaning of
null values without an explicit decision about the upstream data
contract.

## Frontend architecture

Map.jsx is the main map orchestration component. It handles data
loading, responsive state, score controls and map-level coordination.

MapCanvas.jsx renders the map to Canvas.

MapInteraction.jsx contains the existing custom pointer interaction and
D3 interaction integration.

ScoreSheet and ScoreSidebar implement the responsive filter/score
controls.

Preserve the existing component architecture unless a demonstrated
user-facing problem requires a change.

Prefer the smallest targeted change over broad refactoring.

Do not introduce new abstractions, components or libraries when the
existing architecture can solve the problem.

## Responsive behaviour

The intended responsive ranges are:

- below 768px: mobile ScoreSheet
- 768px through 1579px: left-side ScoreSheet
- 1580px and above: permanent ScoreSidebar

Preserve these breakpoint behaviours.

At 768px through 1579px, the Filters control should open the existing
left-side ScoreSheet.

At 1580px and above, the permanent ScoreSidebar should be visible and
the Filters control should not be used.

When changing responsive behaviour, test the breakpoint boundaries
explicitly.

## Map interaction

The existing zoom, pan and boundary behaviour has been deliberately
tuned for this project.

Do not redesign or replace the interaction architecture merely because
React state and D3 maintain separate transform state.

Do not:

- make D3 the sole transform owner
- replace the existing custom pointer dragging
- introduce D3 constrain/translateExtent as an architectural replacement
- rewrite MapInteraction.jsx for architectural cleanliness
- redesign the pan boundary implementation

Only change this interaction architecture if a reproducible,
user-facing problem has been demonstrated and the change is explicitly
requested.

The existing quadtree hit-testing approach is appropriate for the
project's regular equal-sized 20,000 × 20,000 EPSG:3035 grid.

Do not redesign the quadtree or hit-testing approach without evidence of
an actual user-facing problem.

## Canvas rendering and performance

The scored layer contains approximately 11,466 regular grid cells.

The current Canvas rendering approach is intentional.

Do not introduce performance optimisations, change the GeoJSON format,
simplify geometry, introduce binary data, rasterise the data or
redesign the rendering architecture merely because the dataset is
approximately 7.4 MB.

Only pursue such changes when profiling or a demonstrated user-facing
performance problem provides evidence that they are necessary.

## Generated files and dependencies

The following are generated or environment-specific files/directories:

- dist/
- node_modules/
- .DS_Store

Do not manually edit these files.

Do not commit .DS_Store.

dist/ is generated Vite output.

node_modules/ contains installed dependencies.

package-lock.json is tracked and generated by npm, but it may
legitimately change when dependencies are installed or updated. Review
such changes carefully rather than treating them as forbidden.

Do not modify .gitignore merely to hide generated GeoJSON files.
The files in public/data are intentionally tracked runtime assets.

## Git safety

Before making changes:

- inspect git status
- inspect relevant existing changes
- do not revert unrelated user changes

Do not use destructive Git commands.

Do not run git reset, git clean or similar commands that discard work
unless the user explicitly requests it.

Do not run git push unless explicitly requested.

Do not commit changes unless explicitly requested.

Keep changes tightly scoped to the requested task.

## Verification

After implementing a change, run the project's relevant verification
commands.

For frontend changes, run:

- npm run lint
- npm run build

Do not claim a change is fixed unless it has been verified.

For responsive changes, test at least:

- 767px
- 768px
- 1023px
- 1024px
- 1579px
- 1580px

For map changes, preserve and verify:

- data loading
- zoom
- pan
- map boundary behaviour
- hover
- hit testing
- tooltips

When fixing a specific issue, do not use that task as an opportunity to
fix unrelated lint errors, refactor unrelated components, or optimise
unrelated code.

## Current known technical debt

The following are known issues or potential future cleanup items and
should not be changed unless explicitly requested:

- component-score null semantics depend on the upstream data pipeline
- React/D3 transform ownership is not unified
- native D3 gestures are not governed by the same boundary mechanism as
  custom dragging
- the data-loading effect could use AbortController cleanup under
  StrictMode
- there are currently three ESLint errors involving MapInteraction.jsx
  and mapUtils.js
- Canvas redraw performance could potentially be optimised in future if
  profiling demonstrates a real problem

Do not proactively fix these while working on an unrelated task.
